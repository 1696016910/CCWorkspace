# Design

## Context

见 `proposal.md`。基线是已实现的 MVP，本轮不改数据模型，只解决审计中确认的缺陷并把体验补到可交付水平。

## Goals / Non-Goals

**Goals:**

- 任何单点故障（存储损坏、服务不可达、渲染异常）都不应导致应用不可用
- 界面反馈与真实状态一致：不会出现「永久生成中」或「无提示失败」
- 视觉系统可通过主题变量统一驱动，不留硬编码颜色

**Non-Goals:**

- 不引入 UI 组件库
- 不改数据库表结构
- 不做多窗口、多会话并行生成

## Decisions

### 决策 1：数据库损坏采用「备份 + 重建」而非修复

**选择**：`openWithRecovery` 先尝试打开并 `PRAGMA integrity_check`；失败则复制为 `.corrupt-<ts>`、移走原文件、新建空库。

**理由**：SQLite 损坏无法在应用层可靠修复；对个人工具而言，「能启动 + 数据有备份」比「启动失败 + 数据完好」更有价值。

**放弃**：尝试 `recover` 或逐表抢救——实现复杂且成功率低。

### 决策 2：发送走「同步校验 + 异步执行」

**选择**：`chat:send` 先 `assertCanSend`（空消息、并发），通过后 `void send(...)`，回复仅通过 `chat:event` 推送。

**理由**：之前 `await send(...)` 让 IPC 阻塞到整轮结束（实测 11.6 秒），期间输入框一直禁用。拆分后 IPC 21ms 返回，界面即时进入生成态。

**代价**：异步阶段的异常必须显式转发为 `error` 事件，否则会静默丢失。

### 决策 3：超时判定只认「有效事件」

**选择**：只有 `assistant` / `stream_event` / `result` / `system:init` 才算服务已响应；`hook_started` 等不计入。

**理由**：实测连接异常时 CLI 仍会先吐出大量 hook 事件，若把它们计入，超时永远不会触发。

### 决策 4：上下文与命令清单在使用时抓取

**选择**：`/context` 走独立 query，不写入用户消息；命令清单在 `system:init` 时通过 `supportedCommands()` 取全量描述。

**理由**：query 在迭代结束后关闭，之后再调用会报 `Query closed before response received`；必须在迭代期间取值。

**代价**：每个会话首次打开上下文面板会触发一次 `/context`，约 2 万 token。已在 UI 上按需触发，不随会话切换自动执行。

### 决策 5：主题用 CSS 变量 + `data-theme`

**选择**：`:root[data-theme='dark']` 覆盖一组语义变量；组件内不写死颜色，统一用 `var(--surface)` / `var(--line)` 等。

**理由**：无运行时开销，切换即时生效，且能通过 `prefers-reduced-motion` 一并处理动效。

**代价**：新增颜色必须先定义变量，否则暗色下会露白。

### 决策 6：错误边界放在对话区而非全局

**选择**：`ErrorBoundary` 只包裹 `ChatPane`，捕获后显示可重试面板。

**理由**：对话区是渲染最复杂、最可能抛错的部分；把它隔离后，侧栏与设置仍可用，用户能继续操作而不是重开应用。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| `node:sqlite` 依赖 Electron 45 | 版本锁定；打包验证时检查 |
| 超时阈值过短导致长任务被误判 | 只在「从未收到有效事件」时超时，一旦有 token 就不再计 |
| `/context` 消耗 token | 仅在用户主动打开面板且无缓存时触发 |
| 暗色下部分硬编码颜色遗漏 | 审计脚本检查主要区域的计算样式是否随主题变化 |
| 响应式代理无法结构化克隆 | 传给 IPC 前统一展开为普通对象 |

## Migration Plan

无数据迁移。升级后首次启动会自动补齐 schema（已存在），主题默认浅色。

回滚：删除 `workbench.db` 即回到初始状态；`settings.json` 的改动有 `backups/` 可还原。
